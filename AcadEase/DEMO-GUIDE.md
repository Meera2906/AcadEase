## Where everything runs — read this first

This is the single most confusing thing about the setup, so it is stated
plainly before anything else.

### No laptop runs the app locally. Not one.

**Nobody runs `npm run dev`. Nobody opens `localhost:5173`.** All four laptops
open the **Vercel URL** in a browser and do everything from there. During the
ten minutes on stage, every click is on the deployed site.

If a judge asks *"is this running on your laptop?"* the answer is **no** — the
front end is on Vercel's CDN, the API is on Render, the database is MongoDB
Atlas. You can close any laptop mid-demo and the others carry on.

### One laptop also needs a terminal — but not a local server

**L2** must have the repository cloned and a terminal open. Not to run the app —
to run four maintenance commands and to hold the upload files.

| What L2 runs in a terminal | Talks to | Is this localhost? |
|---|---|---|
| `npm run seed` | **Production** Atlas database, via `MONGO_URI` | **No** |
| `npm run seed:governance` | **Production** Atlas database, via `MONGO_URI` | **No** |
| `npm run reset:admissions` | **Production** Atlas database, via `MONGO_URI` | **No** |
| `npm run demo:preflight -- --api …` | **Deployed** Render API over HTTPS | **No** |
| `npm run seed:admissions` | Nothing — writes files to L2's own disk | **No** (local files only) |

Every one of those is a script that reaches out to your **deployed**
infrastructure. None of them starts a web server. The reason they run from a
laptop rather than a button in the UI is that they are destructive
administrative operations, and they deliberately do not have a UI.

### The one and only time localhost appears

**The offline fallback.** If the venue Wi-Fi dies or Render will not wake, L2
runs:

```bash
cd AcadEase/apps/api
npm run e2e:reissue
```

That script **does** start a temporary API server on `127.0.0.1` on a random
port, runs the whole grievance→reissue flow against it, prints 49 assertions,
and shuts down. It is terminal output, not a website — you would be showing the
judges a passing test log, not the app.

It still needs the **Atlas database** to be reachable, so it survives "the site
is down" but not "there is no internet at all."

> **Say this out loud if it comes up:** *"Everything you're seeing is the
> deployed application. The only thing we run locally is the seed script that
> loads demo data into the production database, and that's deliberate — wiping
> and reloading a database isn't something that should be a button in the UI."*

### Files that exist only on L2

`apps/api/demo-data/` — the applicant CSV and 35 document PDFs — is
**git-ignored**. It is generated by `npm run seed:admissions` and exists only on
the machine that ran it. **That machine must be L2**, because L2 is the laptop
that drags those files into the browser. If you generate them on L1 and try to
upload from L2, there is nothing to upload.

## The day before

Work through in order. About 40 minutes the first time. Everything here targets
your **deployed** environment.

### 1. Confirm the deployment is live and current

Both Render and Vercel must be building the latest commit. In any browser:

```
https://YOUR-API.onrender.com/health
```

You want:

```json
{ "status": "ok", "database": "connected", "signingKeyPinned": true }
```

**What each field means:**

- `database: "connected"` — Render can reach Atlas. If it says `disconnected`,
  your Atlas Network Access is not set to `0.0.0.0/0`, or `MONGO_URI` is wrong.
- `signingKeyPinned: true` — the RSA keys that sign certificates are pinned to
  environment variables rather than living on Render's disk. **If this is
  `false`, stop.** Render's free tier wipes its filesystem on every deploy; new
  keys get generated and every certificate issued before that point silently
  stops verifying. Fix with [DEPLOYMENT.md §4](./DEPLOYMENT.md#4-pin-the-signing-keys)
  *before* you seed anything.

### 2. Seed the production database — from L2's terminal

```bash
cd AcadEase/apps/api
MONGO_URI="<your Atlas connection string>" npm run seed
MONGO_URI="<your Atlas connection string>" npm run seed:governance
```

> Both **delete before they write**. Only ever point them at the demo database.

**What each creates:**

- `seed` — 3 colleges, staff and student accounts, courses, attendance history,
  **published** semester results, and a couple of existing certificates. This is
  what makes `STU_2021_CS_001` merit-eligible, which the certificate story
  depends on.
- `seed:governance` — students and faculty for the other two colleges, 258
  applicants spread across the admission pipeline, the 9 college requests
  (including three seat-matrix revisions), and 4 circulars. **Without this the
  Analysis page has one populated row and two nearly empty ones**, which
  undercuts the whole "640 colleges" framing.

### 3. Generate the upload package — **on L2 specifically**

```bash
cd AcadEase/apps/api
npm run seed:admissions
ls demo-data/documents | wc -l      # must print 35
```

This writes files to L2's disk. It puts almost nothing in the database — that is
the point. During the demo you upload this package through the real import path,
so the hashing, flagging and encryption all genuinely happen in front of the
judges rather than being pre-baked.

`demo-data/README.md` lists exactly which flaws are planted in which file. Read
it once; it is your cheat sheet for step 2:00.

### 4. Enrol 2FA on the three staff accounts

`SUP_001`, `ADM_CSE_001` and `FAC_CSE_001` all require TOTP, and **seeding
resets it**. The *first* sign-in after a seed shows a QR enrolment screen — you
do not want that on the projector.

On each staff laptop, at the Vercel URL: sign in → a QR appears → scan with
Google Authenticator, Authy or any TOTP app → enter the 6-digit code. One phone
can hold all three.

Then **sign out and sign in again** to confirm it now asks for a code instead of
showing a QR. If it shows the QR again, the enrolment did not save.

### 5. Clear the admission pipeline — from L2's terminal

```bash
MONGO_URI="<your Atlas connection string>" npm run reset:admissions
```

The demo imports applicants live. If a previous run's applicants are still in
the database, every row is rejected as *"applicantId already submitted by your
university"*.

**That rejection is correct behaviour** — a college must not be able to silently
overwrite applicants it has already submitted — but it is a dead end on stage.
Run this after every rehearsal and again on the morning.

It removes the demo applicants, their document rows, the encrypted files on
disk, the import batches, and any student accounts created by enrolment. It
leaves colleges, staff logins, results and certificates alone.

### 6. Full rehearsal, then reset again

Run the [run of show](#the-run-of-show) end to end with all four laptops. Time
it with a phone. Then `reset:admissions` and do it a second time. The second run
is always three minutes faster.

## Twenty minutes before

### Run the preflight — from L2's terminal

```bash
cd AcadEase/apps/api
npm run demo:preflight -- --api https://YOUR-API.onrender.com --web https://YOUR-WEB.vercel.app
```

This checks your **deployed** stack over HTTPS. It signs in only as the student
— no secrets, no staff credentials — and reports on:

| Section | What it catches |
|---|---|
| Service | API asleep or unreachable; database disconnected; signing keys not pinned |
| Browser wiring | CORS rejecting your Vercel origin; credentials not allowed |
| Student sign-in | Old build deployed (no CSRF token in the body); cookies missing `SameSite=None; Secure` |
| The student's part | No published result to dispute; **student not merit-eligible**; a CSRF-protected form submit failing |
| Staff 2FA | **Which staff accounts will show a QR screen instead of a code prompt** |
| Seeded data | Circulars missing (governance seed not run); public verification unreachable |

You want `READY.` Anything else — read the line, each names its own fix.

### Then, per laptop

| | Setup |
|---|---|
| **All four** | Signed in at the **Vercel URL**. Browser zoom **125%** — judges are three metres away. Every other tab closed. OS notifications off. Laptop plugged in. |
| 🟣 **L1** | Tab 1: **Analysis** (`/admin/analytics`). Tab 2: **Verification** (`/admin/verification`). Tab 3: **College Requests** (`/admin/university-requests`). Tab 4: **Circulars** (`/admin/circulars`). Tab 5: **Certificates** (`/admin/certificates`). |
| 🔵 **L2** | Tab 1: **Bulk Submission** (`/admin/admissions/upload`). Tab 2: **Verify Documents** (`/admin/verification`). Tab 3: **Grievances** (`/admin/grievances`). Plus a file-manager window open on `apps/api/demo-data/`, and a terminal in `apps/api`. |
| 🟢 **L3** | Tab 1: **Mark Attendance** (`/faculty/attendance`) with **CS301 Database Management Systems** already selected. Tab 2: **Verify Certificate** (`/faculty/verify-certificate`). |
| 🟠 **L4** | Tab 1: **Certificates** (`/student/certificates`). Tab 2: **Grievances** (`/student/grievances`). Tab 3: **Attendance** (`/student/attendance`). Phone ready to scan a QR. |

### Keep the API awake

Render's free tier sleeps after 15 minutes idle and takes **30–60 seconds** to
wake — which looks exactly like a crash. Leave the `/health` tab open on L2 and
refresh every few minutes until you are called up. Once anyone is signed in, the
live notification stream keeps it warm on its own.

## Pre-staged state

Ten minutes is not enough to build a certificate from nothing *and* show the
correction story. One thing is staged in advance — **and you say so on stage.**
Staging is normal; pretending is not.

**Before the demo, at the Vercel URL:**

1. 🟠 **L4** → Certificates → request a **merit** certificate, purpose
   *"Scholarship application"*.
2. 🔵 **L2** → Certificates → **Approve**.
3. Stop. It now sits at *"awaiting TNTEU"*.

During the demo, L1 counter-signs it live — one click — and the PDF is generated
in front of the judges. You show the *finish* of the signing chain without
spending ninety seconds on its setup.

**Everything else in the run is genuinely live.**

## The run of show

Each step has:

- **DO** — the exact clicks
- **SAY** — the narration (your words, this substance)
- **What is actually happening** — so you can answer follow-ups with confidence
- **Look for** — how you know it worked
- **Cross-questions here** — what a judge is most likely to ask at this exact moment

Times are cumulative from zero.

### 0:00 – 0:40 · The problem 🟣 L1

**DO** — On **Analysis** (`/admin/analytics`). Point at the three college rows,
then the totals strip at the top.

**SAY**
> TNTEU is an affiliating university. It doesn't teach anyone — it oversees 640
> B.Ed and M.Ed colleges, and it's the super admin of this entire system. When
> students apply for admission, the colleges send their documents to TNTEU, and
> TNTEU's *teaching staff* cross-check every single one by hand. That's the
> bottleneck we were asked to solve. Not digitisation — the colleges already
> send PDFs. The bottleneck is the person who has to open each one.
>
> This is the regulator's chair. Three colleges here; at 640, this page *is* the
> job.

**What is actually happening.** One request to `/api/admin/analytics/colleges`.
The server runs one aggregation per collection — not one query per college — so
the page cost does not grow linearly with the number of colleges. Attendance is
averaged **per student first, then per college**, because a straight
record-level average silently over-weights departments with heavier timetables.

**Look for** — three colleges with visibly *different* numbers: seat fill around
39% / 64% / 48%, attendance around 89% / 92% / 75%. If all three look identical
or empty, `seed:governance` did not run.

**Cross-questions here**

- *"Is this real data or a mockup?"* — Real, from the database. Every figure is
  computed at request time; there are no hardcoded numbers on this page. We can
  hit the API directly and show you the same JSON.
- *"Why only three colleges?"* — That is our seeded demo set. The queries are
  aggregations that group by college, so 640 is the same number of queries as 3.
  We have not load-tested 640, and we will not claim we have.
- *"What's the 75% attendance college?"* — Vellore. Seeded deliberately lower so
  the page has contrast; the chronic-absentee count next to it is what a
  regulator would act on.

### 0:40 – 2:00 · One CSV, one folder 🔵 L2

**DO** — **Bulk Submission** (`/admin/admissions/upload`) → choose
`demo-data/applicants.csv` → **Import applicants**. Then drag all 35 files from
`demo-data/documents/` into the second box → **Upload documents**.

**SAY**
> I'm the college office at Kongu College of Education. One CSV of applicants,
> one folder of their documents. The files are named
> `applicantId__documentType`, so the server matches each file to the right
> applicant automatically — nobody sits there pairing them up.

**DO** — Point at the import report: **7 imported, 2 rejected**.

**SAY**
> Two rows rejected, each with its reason on the row: one has an unsupported
> programme, one has no applicant ID. The college can see exactly what to fix.
> Nobody emails back asking what went wrong.

*(The 35 documents take a few seconds. Talk over it.)*

> While that runs — every file is being hashed, checked, encrypted and stored.
> The encryption is sealed for TNTEU and this college only.

**What is actually happening.** The CSV is parsed row by row; each row is
validated independently, so one bad row never aborts the batch. Each document is
then SHA-256 hashed, checked for legibility, scanned for a QR, text-extracted,
run through the flag rules, envelope-encrypted, and written under
`secure-storage/admission-docs/` with a random filename. The client's filename is
kept only as a label, never used on disk.

**Look for** — `7 imported · 2 rejected · 9 total`, then
`35 imported · 5 flagged for review · 0 rejected`.

**If it says 0 imported / 9 rejected** — the pipeline was not reset. The screen
now explains this itself. Read the explanation out loud, say *"the system
refuses to let a college silently overwrite applicants it already submitted"*,
and move straight to the document upload, which still works.

**Cross-questions here**

- *"What if two colleges use the same applicant ID?"* — Rejected as *"already in
  use by another university"*. IDs are unique system-wide, not per college.
- *"Can a college overwrite a submitted applicant?"* — No. That is the rejection
  you may have just seen. Documents can be replaced; the applicant record cannot
  be silently rewritten.
- *"What if the filenames are wrong?"* — The file is reported as unmatched in
  the report rather than being guessed at. Roll number works in place of the
  applicant ID.
- *"Where are these files stored?"* — Encrypted at rest on the server, wrapped
  for TNTEU and the submitting college. Not in the database, not on a public
  URL. Opening one in a text editor gives you ciphertext.
- *"Could the applicant upload these themselves instead?"* — **Yes, and that
  path is built.** `/apply` is a self-service portal where an applicant
  registers, uploads their own documents and tracks status on a scoped session
  that expires the moment they are enrolled. Both doors run identical checks and
  land in the same queue. Bulk is for a college processing its intake; the
  portal is for a college with no office capacity.

### 2:00 – 3:30 · The flags, and the gate 🔵 L2 — *the core claim*

**DO** — **Verify Documents** (`/admin/verification`). The queue is already
sorted flagged-first.

**SAY**
> 35 documents in. Five are flagged. The queue puts them at the top — I never
> have to go looking.

**DO** — Open **APP_2025_003's 10th marksheet** (flagged `duplicate_hash`).

**SAY**
> This is a byte-for-byte copy of a different applicant's marksheet. SHA-256 —
> not a guess, not a model's opinion. And it names the applicant it matches, so
> I can go and look at both.

**DO** — Back to the queue. Point at the other four in turn: `name_mismatch` on
APP_2025_004's transfer certificate, `missing_field` on 005's 12th marksheet,
`unreadable` on 005's ID proof, `expired_document` on 006's community
certificate.

**SAY**
> Nine checks, all deterministic. A hash comparison. A name comparison. A date
> comparison. A required-document checklist. Same input, same answer, every
> time — and every one can be explained to a rejected applicant in one sentence.
>
> **We deliberately did not put an LLM in this decision.** A model that says
> "this marksheet looks genuine" and is wrong costs a real student their
> admission, and you can't audit it, reproduce it, or tell them why. Where we do
> extract text, it's a pre-fill for a human — if a document can't be read, it's
> flagged `unreadable` and routed to a person. Uncertainty escalates. It never
> resolves itself.

**DO** — Select all → **Approve all eligible**.

**SAY**
> Thirty clear in one action. The five flagged ones are **refused** — the gate
> will not let them through in bulk. They have to be opened and decided one at a
> time.
>
> That is the whole thesis. The machine clears what is provably fine and hands
> the human the ones that need judgement. Nothing was auto-approved.

**DO** — Open APP_2025_001's documents and approve them individually.

**What is actually happening.** The queue is sorted `flagCount: -1, createdAt: 1`
— flagged first, then oldest — and there is a compound index built for exactly
that sort, so it does not degrade as the backlog grows. `Approve all eligible`
selects only `flagCount: 0` documents, up to 200 per sweep. Every approval, bulk
or individual, **re-hashes the stored file and re-checks for duplicates at
decision time** — so a file swapped after upload fails the approval rather than
riding through it.

**Look for** — the flagged five listed in the "held back" summary after the
sweep, each with its reason.

**Cross-questions here**

- *"So the system never approves anything?"* — Correct. It decides what deserves
  attention; a human decides what is true. The only code paths that mark a
  document `verified` require an authenticated reviewer.
- *"Why nine checks and not more?"* — Those are the ones we can make
  deterministic today. Anything requiring judgement is routed to a person rather
  than guessed at. More rules is easy; more *reliable* rules is the constraint.
- *"What stops someone approving a flagged document?"* — Nothing, and that is
  intentional. A reviewer can approve a flagged document after opening it —
  duplicate hashes have innocent explanations. What they cannot do is approve it
  *without looking*, which is what bulk approval would allow.
- *"How much time does this actually save?"* — In this batch, 30 of 35 documents
  never needed a human at all. The honest framing: it does not make review
  faster, it removes review from the documents that did not need it.
- *"What if someone tampers with a file after upload?"* — Approval re-hashes the
  file first. A mismatch is a `409`, and the document is permanently marked
  `integrity_failed` and can never be bulk-approved again. We can demonstrate
  this — see [Prove it on demand](#prove-it-on-demand).
- *"Isn't a hash check trivially defeated by changing one pixel?"* — Yes, and we
  say so. `duplicate_hash` catches lazy reuse of the same file, which is the
  common case. Catching a re-scanned forgery needs the issuing board's registry,
  which is our number-one roadmap item.

### 3:30 – 4:30 · Two stages, two institutions 🟣 L1

**DO** — **Verification** (`/admin/verification`). The documents L2 just approved
are now here.

**SAY**
> Now I'm TNTEU. What's on my desk is only what the college has already stood
> behind. Stage one is theirs, stage two is mine. Before they approved, this
> queue was empty — I could not have seen these documents at all.

**DO** — **Approve all eligible**.

**SAY**
> Only a TNTEU approval can mark a document *verified*. A college can't approve
> on TNTEU's behalf, and TNTEU can't skip the college.

**What is actually happening.** Both stages use the *same two screens*. Which
documents you see, and whether the buttons are live, is decided by the server
from your role — never from the route or a URL parameter. That is why a college
admin cannot reach stage two by typing a different address.

**Look for** — the count on TNTEU's queue matching what L2 approved. Documents
L2 did not approve are absent, not greyed out.

**Cross-questions here**

- *"Why two stages? Isn't that just slower?"* — It moves the first pass to the
  people who know the applicant. TNTEU's staff time is the scarce resource; the
  college's own office is not. It also creates accountability: the college has
  signed for these documents before TNTEU ever sees them.
- *"Could the college and TNTEU be the same person?"* — Not with these accounts.
  Each stage records who acted, with which institution's key. The same human
  logged into both accounts would leave two distinct signed records.
- *"What if TNTEU rejects something the college approved?"* — It goes back with
  a reason, and the reason is part of the signed record — it cannot be rewritten
  later.

### 4:30 – 5:30 · A certificate nobody can forge 🟣 L1 → 🟠 L4

**DO — L1** — **Certificates** (`/admin/certificates`) → the pending merit
request → **Approve**.

**SAY (L1)**
> This student asked for a merit certificate, their college approved it, and
> it's been waiting for my counter-signature. Now the PDF gets generated —
> server-side, and only after both signatures exist. There was no PDF a moment
> ago.

**DO — L4** — **Certificates** (`/student/certificates`) → refresh → download it
→ **scan the QR with a phone** (or open `/verify/<certId>` in a new tab).

**SAY (L4)**
> Anyone can check this. No login.

**SAY (L1)** — pointing at the verification page
> Name, type, date, both institutional signatures. And **no marks, no
> attendance, no contact details** — an employer verifying a certificate has no
> business seeing any of that.
>
> Underneath, each institution signs its own decision *plus the signature before
> it*. Remove a stage, reorder them, or edit an approval, and every signature
> after it breaks. It's RSA, not a shared secret — anyone can verify, only the
> key holder can sign.

**What is actually happening.** Merit eligibility is checked **server-side**
against published results (≥75%, no arrears) — a student cannot request one they
have not earned. The PDF is generated with `pdfkit`, a QR pointing at
`/verify/<certId>` is embedded, the finished file is SHA-256 hashed and that hash
is stored, and TNTEU signs the certificate itself as a final link on the
approval chain.

**Look for** — the public verification page loading **in a private window or on
a phone**, with no login. That is the point; do not verify it while logged in.

**Cross-questions here**

- *"Can a certificate be faked?"* — You would need TNTEU's private key.
  Verification is public, signing is not. That is exactly why the chain is RSA
  rather than the HMAC we started with — with a shared secret, anyone who can
  *check* a certificate can also *mint* one.
- *"What if someone edits the PDF?"* — Two answers. The record still verifies
  because the QR is genuine — so we also hash the file. Faculty have a **Verify
  Certificate** screen that compares the uploaded file against the hash of the
  PDF we generated and reports the mismatch. We show that at 6:55.
- *"What stops a student requesting a merit certificate they don't deserve?"* —
  The server evaluates it against published results and refuses with the reason.
  It is not a form field they can fill in.
- *"Why is nothing generated until both approve?"* — So a partially-approved
  certificate never exists as a file. There is no draft PDF to leak.

### 5:30 – 6:55 · The payoff 🟠 L4 → 🔵 L2 → 🟠 L4

**Slow down here.** This is the part that distinguishes the project. Do not rush
it to save thirty seconds.

**DO — L4** — **Grievances** (`/student/grievances`) → New → Category
**Academic** → in the *"Which result is this about?"* dropdown pick **Semester 4
— 2023-2024** → Subject: *"Databases mark entered as 88 instead of 94"* →
Submit.

**SAY (L4)**
> I'm disputing a mark. Notice the form asked me *which result* — that link
> matters in about thirty seconds.

**DO — L2** — **Grievances** (`/admin/grievances`) → **Acknowledge**. Then stop
and point at the warning panel that appears.

**SAY (L2)**
> Here's the problem every one of these systems has. If I correct this mark, the
> merit certificate that was issued *from* that mark is now wrong — and it's a
> signed PDF that is already out in the world, in somebody's job application.
>
> The system is telling me before I act: **one active certificate was issued
> from this record.**

**DO — L2** — Tick **"the result record was corrected"**, write a resolution note
(*"Revaluation applied: CS302 corrected from 88 to 94"*), **Resolve**.

**SAY (L2)**
> Resolving with that box ticked revokes the old certificate as **superseded**
> and issues a replacement — signed the same way, through the same path.

**DO — L4** — **scan the OLD QR again** (the phone still has it, or reopen the
old tab).

**SAY (L4)**
> The old certificate still answers. It doesn't 404, and it doesn't say
> "revoked" — it says **superseded, a corrected certificate was issued**, and it
> links to the replacement. That distinction matters: this student did nothing
> wrong; the college did. A red "revoked" would imply misconduct.

**DO — L4** — Follow the link to the replacement, then go to **Certificates** —
it is already in the list.

**SAY (L1, closing the beat)**
> Nothing was edited. Nothing was deleted. The old record keeps its original
> snapshot and its original signature, and the new one still carries the
> college's original approval inside its chain.
>
> And nobody had to *remember* to do it. That's the point — this is exactly the
> manual step that gets forgotten, and when it's forgotten, a wrong signed
> certificate stays valid indefinitely.

**What is actually happening.** On resolve, the server looks up active
certificates for that student whose *type* derives from the disputed *record
kind* — a corrected result affects `merit` and `completion`, and deliberately
never touches `bonafide` or `character`, because those assert "this person is
our student", which a mark does not change. Each affected certificate is revoked
with `revocationType: "superseded"`, a replacement is generated with a fresh
HMAC, a new QR and a new signed `reissued` link appended to the *existing* chain,
and the two are linked in both directions. It is idempotent: resolving twice does
not revoke the replacement.

**Look for** — the toast saying *"1 certificate superseded and reissued"*, and
the grievance card listing `oldCertId → newCertId`.

**If nothing reissues** — the grievance did not name a result (was it
**Academic**, with a result actually selected?), or the box was not ticked. Raise
it again correctly; it takes forty seconds.

**Cross-questions here**

- *"Where did the mark actually get corrected?"* — Faculty re-enter and republish
  the result; that is the college's existing process. What we built is the
  consequence: the admin confirms the record was corrected when they resolve, and
  the certificate reissue follows automatically. **We are not claiming to have
  automated revaluation.** We automated the thing everyone forgets afterwards.
- *"What if the college ticks the box without correcting anything?"* — Then they
  have issued a fresh certificate with identical content and left a signed audit
  entry saying they did it — recorded against the grievance, the audit log, and
  both certificates. It is not a way to hide anything.
- *"Why not just edit the certificate?"* — Because it is signed. Editing it
  breaks the signature, and a certificate whose signature does not verify is
  indistinguishable from a forgery. Revoke-and-reissue is the only correction
  that preserves the guarantee.
- *"What about a grievance that isn't about a mark?"* — It cannot touch a
  certificate at all. The reissue only runs when the grievance names a record,
  and only for certificate types derived from that kind of record. A complaint
  about a broken projector is structurally incapable of triggering it.
- *"Does the employer who already checked the old one get told?"* — No, and that
  is an honest gap. What they get is a truthful answer if they check again — the
  old QR reports supersession and points at the replacement. Active notification
  of past verifiers is not built.
- *"What if there are two reissues in a row?"* — The chain extends each time and
  the lineage is walked when verifying, so a certificate reissued twice still
  validates its full history back to the original college approval.

## When something breaks

| What happens | Why | Do this |
|---|---|---|
| **First click hangs 30–60s** | Render free tier was asleep | Keep talking — the 0:00 framing covers it. Happens once only. |
| **CSV imports 0 of 7** | Pipeline not reset | The screen explains it. Read it out, call it correct behaviour, move to the document upload. |

| **"CSRF token missing or invalid"** | Deployed build predates the fix | Redeploy **both** Render and Vercel. Nothing else fixes it. |
| **Someone gets logged out** | Cross-site cookie dropped | Sign back in. If it repeats, `COOKIE_CROSS_SITE=true` is missing on Render. |
| **"Too many failed attempts"** | Rate limit on shared Wi-Fi | Wait 60s. Only *failed* logins count, so somebody is mistyping a password. |
| **Certificate download 404s** | PDF was on ephemeral storage, wiped by a redeploy | **Verify by QR instead** — it still works, and it is the stronger artefact anyway. |
| **The reissue doesn't fire** | Grievance named no result, or box unticked | Raise it again correctly. 40 seconds. |
| **Analysis page looks empty** | `seed:governance` not run | Skip to bulk submission; come back if there is time. |
| **Whole site unreachable** | Wi-Fi or Render | 🔵 L2 runs `npm run e2e:reissue` — a **local** temporary server, printing 49 passing assertions. Say plainly: *"the site is unreachable, so this is the same flow running as an automated test."* Needs Atlas reachable. |

## General cross-questions

The step-specific ones are inline above. These come at the end.

**"Why not use AI to verify the documents?"**
> Because an LLM that says a marksheet is genuine and is wrong costs a real
> student their admission, and there is no way to audit, reproduce or explain
> that decision. Every check here is a hash comparison, a string comparison, a
> date comparison or a checklist. Same input, same answer, every time. Where we
> extract text it is a pre-fill for a human — unreadable documents are flagged
> and routed to a person, never guessed at.

**"Does this scale to 640 colleges?"**
> The queue, the indexes and the aggregations are built for it, and tenant
> scoping happens per query rather than per response, so it does not degrade as
> colleges are added. Honestly: the largest dataset we have run is 3 colleges,
> 153 students, 267 applicants. We have not load-tested 640.

**"What stops one college seeing another's data?"**
> The query is rewritten before it reaches the database, so the record is absent
> from the result set rather than filtered out of the response. Direct fetch by
> ID returns 404. We can show you in twenty seconds.

**"What's not built yet?"**
> DigiLocker or state-registry integration is the big one. Today we can prove two
> applicants submitted the same file; we cannot prove a marksheet matches what
> the board actually recorded. We already generate the lookup handle for a
> reviewer to check by hand — the automated round-trip is the missing piece and
> the single biggest jump in verification strength available to us. Also:
> attendance-driven reissue, reissue when faculty correct a mark without a
> grievance, and trend analytics over time.
> [PITCH.md §7](./PITCH.md#7-whats-next) has the full list.

**"Is this running on your laptop?"**
> No. The front end is on Vercel, the API is on Render, the database is MongoDB
> Atlas. Every laptop here is just a browser. The only thing we run locally is
> the seed script that loads demo data into the production database — and that
> is deliberate, because wiping and reloading a database should not be a button
> in the UI.

**"How much of this is actually working versus mocked?"**
> Everything you have seen writes to the database and reads back from it. There
> are no static screens in the demo. We removed a design mockup that used
> invented numbers precisely so nothing on screen is fictional. 81 unit tests and
> 6 end-to-end suites, all passing — we can run them now.

**"Who did what?"** — Have this answer ready and honest. Four names, four areas.
